# Catch-up note — labgate device control plane

**As of** 2026-09-11 · **head** `a6b2a22` · **pushed to** `origin/main` and
`photonics/main` (both at the same commit) · **179 tests pass**

Read this first if you are picking the project up mid-stream. It is a map,
not a manual: each section points at the document or module that holds the
detail.

---

## 1. What the platform is

`labgate` is a deterministic API gate in front of a two-photon-polymerisation
laser rig (SPiiPlus stage, Phoebe-controlled laser, Hikrobot MV-CS200-10GC
camera, white light). The governing idea is a **trust boundary**: an AI or a
notebook may *propose*, but only deterministic code validates, approves and
executes. Layer model (L0–L3) is in `Docs/technical/02-detailed-technical-documentation.md`.

## 2. There are now TWO control planes. This is the thing to understand.

| | **Plan path** (original) | **Device path** (added this week) |
|---|---|---|
| Entry | `POST /plans` → approve → execute | `POST /devices/{id}/actions/{action}` |
| Unit of work | declarative `ExperimentSpec` | one action on one device |
| Governed by | **human approval**, `proposer != approver` | **risk tier** |
| Purpose | running an experiment | bringing the rig up, diagnosing, testing by hand |
| Code | `spec.py`, `validation.py`, `plans.py`, `execution.py` | `actions.py`, `devicectl.py`, `devices/declarations.py` |

The device path exists because there was no way to *enable the stage axes* over
the API — `StageTcp.enable_axes`/`commutate` existed in the driver but were
never exposed, so the servos were never energised and "the stage won't move"
had no API-level remedy. Design note: `Docs/plans/2026-09-11-device-control-plane.md`.

## 3. The action surface

Actions are **declared as data** in `devices/declarations.py`, which both
`devices/sim.py` and `devices/rig.py` import. That shared declaration is what
guarantees a call accepted in simulation is accepted on the rig
(`test_rig_and_sim_declare_the_same_action_surface` enforces it). An action
named `jog` is implemented by a method named `act_jog` — the `act_` prefix is
what keeps the network-reachable surface explicit.

```
stage        enable_axes[prepare], home[motion], jog[motion], move_relative[motion],
             move_absolute[motion], set_velocity[prepare], set_acceleration[prepare],
             set_jerk[prepare], halt[motion], position[read]
laser        set_power[prepare], output_off[prepare], status[read], output_on[EXPOSE]
camera       snapshot[read], set_exposure[prepare], set_gain[prepare],
             set_auto_exposure[prepare], settings[read]
white_light  set_on[prepare]
```

Discover them live at `GET /devices/{id}/actions` — bounds, units and
requiredness come back with each parameter. The static OpenAPI spec
(`Docs/openapi.json`) deliberately types that route as `list[dict]`: runtime
discovery is how a client grounds itself, so the declarations are the source
of truth, not the spec.

## 4. The safety model — do not erode this

**Tiers → minimum role** (`devicectl.TIER_ROLE`):

- `read` — any authenticated role
- `prepare` — operator
- `motion` — operator, and interlocked
- `expose` — **admin only**. Exactly one action in the whole system is
  `expose`: `laser.output_on`. A test asserts that nothing else quietly
  acquires the power to open a shutter.

**Interlocks**, applied in `DeviceControl.invoke()` in a fixed order (the
docstring at the top of `devicectl.py` lists all eight checks):

- `blocked_during_run` — exclusivity with the executor. **Nobody overrides
  this, admin included.** Interleaving with a running plan can corrupt an
  exposure; this is a correctness invariant, not a policy.
- `blocked_when_beam_on` — motion is refused while the beam is live. An
  **admin may override** this (they have to, or physical testing is
  impossible), and the override is written to the audit log as
  `interlock_override` rather than passing silently.
- `always_allowed` — stop paths (`halt`, `output_off`, `/system/estop`).
  These bypass both interlocks **and the per-device lock**. The executor
  holds that lock for an entire line traverse, so a stop that took the lock
  would queue behind the exposure it is trying to interrupt.

**Conservative beam reading.** `LaserController.is_on` returns `None` when a
toggle failed to confirm. `None` means UNKNOWN and is treated as *possibly
live* everywhere — `_beam_is_on()` returns `True` for it. Never coerce it to
a bool on the way through.

`connect`/`disconnect` are motion in disguise (connect enables axes and moves
to origin; disconnect homes first), so they run through
`devicectl.guard_lifecycle()` and carry the same interlocks.

## 5. Running it

Tokens live in `config/tokens.yaml`, referenced by `tokens_file` in
`config/default.yaml`. Three identities are provisioned: `darina` (operator),
`tatevik` (approver), `narek` (admin). Generate more with
`python -c "import secrets; print(secrets.token_urlsafe(24))"`.

> The tokens file is **tracked in git by the user's explicit decision**. Do
> not untrack, rotate or rewrite history over it without asking them first.

`mode: sim` runs the whole platform with no hardware and no vendor SDKs.
Vendor imports (`SPiiPlusPython`, `MvCameraControl_class`) are lazy, so the
platform starts on any machine; the camera silently falls back to `SimCamera`
when the MVS SDK is absent.

## 6. Bringing the rig up over the API

Full runbook: `Docs/deployment/rig-bring-up-over-api.md`. The shape of it:

1. `GET /system/preflight` — says what is wrong and, per check, whether the
   remedy is an API call or something a human must do with their hands
   (`manual: true`, e.g. "turn the key switch on the laser head").
2. `POST /devices/{id}/connect` for each device.
3. `POST /devices/stage/actions/enable_axes` — **the step that was missing**.
4. `POST /devices/{id}/diagnose` — read-only, never actuates.
5. Then either drive by hand through the device path, or submit a plan.

`POST /system/estop` closes the beam, aborts and *waits for* the run, then
safe-states a second time, and tells you `still_running` if a plan outlived
the 15 s timeout.

## 7. Most recent work (commit `a6b2a22`)

A code review of the control plane produced nine findings, all confirmed real
and all now fixed. Seven of them could have put the beam or the stage
somewhere the operator did not ask for — the worst were: an UNKNOWN beam
state being coerced to "off" and read by the motion interlock; stop paths
queueing behind the device lock; estop returning "ok" while a cooperative
abort had not yet been observed and could re-open the shutter.

`tests/labgate/test_review_regressions.py` has one test group per finding,
each docstring stating what *used* to happen. Every test in it was verified
by re-introducing its bug and confirming the test goes red — so they are
load-bearing, not incidentally green. **If you touch the interlocks, that
file is the specification.**

## 9. Conventions worth not breaking

- Bounds live next to the hardware they protect (`devices/`), never in the
  API layer.
- `ValidationFailed` → 422. Anything that is not a `LabgateError` falls to
  500, so "which exception type comes out" is part of the API contract. A
  parameter the validator admits but the adapter cannot execute is a bug —
  that was review finding 8 (axis gaps: `[0, 2]` must not admit `1`).
- The audit log is append-only JSONL and records intent *before* motion
  happens, so a fault mid-move still leaves a trace.
- Anything that opens the shutter outside an approved plan is audited
  distinctly as `beam_opened_manually`.
